# NoPlanner 제품 기획서

## 1. 제품 개요

NoPlanner의 첫 번째 제품은 개발자가 회사에서 전달받은 서비스 기획서를 구현하기 전에, 해당 기획이 현실적으로 성립하는지 독립적으로 조사하고 평가하는 도구다.

문서를 요약하거나 문장을 교정하는 데 목적이 있지 않다. 기획서가 전제로 삼은 문제, 사용자, 시장, 데이터, API, 기술, 비용, 정책과 운영 조건을 실제 자료와 대조하고, 구현을 시작해도 되는지를 판정한다.

## 2. 배경과 문제

개발자는 회사에서 전달받은 기획서를 구현하는 과정에서 다음 문제를 뒤늦게 발견한다.

- 무엇을 왜 만드는지 정의되지 않았다.
- 해결하려는 문제가 실제로 존재한다는 근거가 없다.
- 대상 도메인, 국가, 시장과 사용자 환경이 반영되지 않았다.
- 논문, 해외 사례 또는 벤치마킹 결과를 현재 환경에 적용할 수 없다.
- 필요하다고 가정한 데이터가 없거나 확보할 수 없다.
- 핵심 기능에 필요한 API 또는 기술이 존재하지 않는다.
- 예산, 일정, 인력과 운영 조건으로 구현할 수 없다.
- 문서 내부의 정책, 요구사항과 일정이 서로 충돌한다.
- AI가 생성한 문장이 검증 없이 기획서에 포함되어 있다.
- 개발자가 누락된 정책과 예외 처리를 다시 기획해야 한다.

이러한 문제는 구현이 시작된 뒤 재작업, 일정 지연과 책임 분쟁으로 이어진다. NoPlanner는 개발자가 직접 모든 근거를 다시 조사하고 문서 전체를 검증해야 하는 비용을 줄이고, 잘못된 기획이 개발 단계로 넘어오기 전에 차단한다.

## 3. 첫 사용자

### 3.1 주요 사용자

첫 사용자는 서비스 기획서를 전달받아 구현 가능성과 요구사항을 검토해야 하는 개발자다.

사용자는 기획 경험이 있어 문제를 감지할 수 있지만, 다음 작업을 매번 직접 수행하기 어렵다.

- 긴 문서에서 핵심 주장과 전제를 모두 추출하기
- 도메인과 시장 자료 조사하기
- 데이터 및 API의 실제 존재와 사용 조건 확인하기
- 기술 구현 가능성과 비용 확인하기
- 문서 여러 위치에 흩어진 모순 찾기
- 문제를 평가자에게 설명할 근거 정리하기

### 3.2 확장 사용자

초기 기능이 안정화되면 다음 사용자가 같은 통합 평가 리포트를 사용할 수 있다.

- 기획 작성자
- 개발 책임자와 기술 검토자
- 프로젝트 관리자
- 승인권자와 경영진
- 디자인 및 운영 담당자

사용자별로 사실이나 결론을 다르게 제공하지 않는다.

## 4. 첫 평가 대상

첫 평가 대상은 회사 내부에서 작성된 서비스 기획서다.

기획서와 함께 다음 자료를 선택적으로 입력할 수 있다.

- 요구사항 정의서
- 정책서
- 화면 설계서와 프로토타입
- 사용자 흐름
- 시장조사 및 벤치마킹 자료
- 논문과 통계
- 회의록과 의사결정 기록
- 기술 검토 자료
- 일정과 예산
- 기존 서비스 및 시스템 문서

문서가 하나만 입력되어도 평가를 시작한다. 필요한 맥락이 누락되면 외부 조사로 확인하고, 외부에서도 확인할 수 없는 내용은 미검증 전제로 분류한다.

## 5. 제품 목표

1. 구현 전에 기획의 치명적인 결함을 발견한다.
2. 모든 주요 판정에 확인 가능한 근거를 제공한다.
3. 개발자가 기획서를 다시 분석하지 않아도 핵심 문제를 파악하게 한다.
4. 작성자와 평가자가 동일한 리포트로 문제를 논의하게 한다.
5. 수정본에서 기존 문제가 해결되었는지 재검증한다.
6. 장기적으로 검증 능력을 자율 기획과 제품 설계에 재사용한다.

## 6. 비목표

초기 버전은 다음을 목표로 하지 않는다.

- 맞춤법과 문장 표현 중심의 교정 도구
- 문서 분량과 템플릿 준수 여부만 확인하는 체크리스트
- 근거 없이 단일 점수를 생성하는 평가 도구
- 작성자의 성격, 태도 또는 의도를 추측하는 인사 평가 도구
- 기획서의 주장을 사실로 전제하고 개발 작업만 생성하는 도구
- 모든 도메인에 대한 자체 정답 데이터베이스를 처음부터 구축하는 것

## 7. 핵심 사용자 흐름

```text
프로젝트 생성
→ 기획서 및 참고자료 입력
→ 대상 환경과 제약 확인
→ 문서 구조·주장·전제 추출
→ 내부 일관성 검사
→ 조사 계획 자동 생성
→ 웹·공공데이터·공식 문서·벤치마킹 조사
→ 데이터·API·기술·시장 현실성 검증
→ 문제별 근거·심각도·신뢰도 결정
→ 통합 평가 리포트 생성
→ 사용자의 근거 확인 및 이의 제기
→ 수정본 입력
→ 변경점과 문제 해결 여부 재평가
```

## 8. 입력

### 8.1 필수 입력

- 하나 이상의 기획 문서 또는 직접 입력한 기획 내용

### 8.2 권장 입력

- 적용 국가 및 지역
- 서비스 도메인
- 대상 사용자
- 프로젝트 목표
- 현재 기획 단계
- 예상 일정과 예산
- 사용 가능한 인력과 기술
- 보유 데이터 및 시스템
- 반드시 지켜야 할 조직 정책

권장 입력이 없으면 문서에서 추출한다. 추출할 수 없으면 조사를 통해 추정하되, 추정값임을 표시하고 판정의 신뢰도에 반영한다.

## 9. 문서 분석

입력 문서에서 다음 요소를 구조화한다.

| 추출 대상 | 설명 |
|---|---|
| 문제 | 해결하려는 현상과 원인 |
| 목적 | 왜 이 기획을 수행하는지 |
| 목표 | 달성하려는 측정 가능한 결과 |
| 대상 | 사용자, 고객, 이해관계자와 적용 환경 |
| 주장 | 문서가 사실 또는 결론으로 제시한 내용 |
| 근거 | 주장에 연결된 출처와 데이터 |
| 전제 | 기획이 성립하기 위해 참이어야 하는 조건 |
| 해결책 | 제안된 기능, 정책과 운영 방식 |
| 의존성 | 데이터, API, 기술, 권한과 외부 협력 |
| 제약 | 일정, 비용, 법률, 보안과 조직 조건 |
| 성공 기준 | 결과를 판단할 지표와 인수 조건 |
| 미결정 사항 | 문서에서 결정되지 않거나 충돌하는 내용 |

각 항목은 원본 문서 위치와 연결하여 사용자가 판정 근거를 역추적할 수 있어야 한다.

## 10. 조사 원칙

NoPlanner는 판정에 필요한 범위에서 가능한 모든 신뢰할 수 있는 자료를 조사한다. 빠른 답변보다 정확성과 검증 가능성을 우선한다.

### 10.1 조사 대상

- 정부 및 공공기관 데이터
- 법령, 행정규칙과 정책 자료
- 국가통계와 국제기구 통계
- 공식 API 및 기술 문서
- 원문 논문과 학술 자료
- 기업의 공식 제품·가격·정책 문서
- 산업 보고서와 시장 자료
- 대상 국가와 도메인의 실제 서비스
- 경쟁 및 유사 서비스 벤치마킹
- 오픈 데이터셋과 데이터 카탈로그
- 오픈소스 저장소와 구현 사례
- 필요할 경우 조직 내부 문서와 보유 데이터

### 10.2 근거 우선순위

1. 원천 데이터와 직접 확인 가능한 사실
2. 정부, 공공기관, 표준기관과 공식 문서
3. 원문 논문과 재현 가능한 연구
4. 공급자 공식 문서와 실제 제품 조건
5. 신뢰할 수 있는 2차 분석 자료
6. 사용자 사례와 비공식 자료
7. LLM의 추론

하위 근거만 존재하면 그 사실을 표시하고 신뢰도를 낮춘다. LLM의 기존 지식만으로 외부 사실을 확정하지 않는다.

### 10.3 사실성 기준

- 모든 외부 사실에 출처와 확인 시점을 기록한다.
- 통계는 조사 대상, 지역, 기간과 표본을 확인한다.
- 논문은 연구 조건과 기획 대상 환경의 차이를 확인한다.
- 해외 사례는 법률, 문화, 시장과 데이터 환경의 차이를 확인한다.
- API는 실제 문서, 제공 기능, 가격, 제한, 폐지 여부와 이용 조건을 확인한다.
- 데이터는 존재 여부뿐 아니라 접근 권한, 형식, 품질, 범위와 갱신 주기를 확인한다.
- 데이터의 `존재`, `실제 접근 가능`, `비용 감당 가능`, `상업적 이용 가능`을 서로 다른 조건으로 검증한다.
- 무료 데이터도 라이선스 원문과 이용약관에서 상업적 이용, 가공, 파생 결과 제공, AI 처리, 저장과 재배포 허용 여부를 확인한다.
- 기획서의 수치는 대상·단위·지역·기간·표본과 계산 기준을 분리해 원문 통계·논문·공시에서 확인한다.
- 핵심 주장에는 가능하면 서로 독립적인 출처를 교차 검증한다.
- 검색 결과는 원출처를 찾기 위한 탐색 수단으로만 사용하며, 공식 데이터 페이지·가격표·이용약관·논문 원문·공시까지 이동해 내용을 직접 확인한다.
- 사실, 해석, 추론과 미확인 사항을 명시적으로 구분한다.

### 10.4 조사 종료 조건

“모든 것을 조사한다”는 범위가 무한해지는 것을 방지하기 위해 다음 조건을 만족할 때 조사를 종료한다.

- 기획의 핵심 전제마다 확인 결과 또는 확인 불가 사유가 있다.
- 차단 가능성이 있는 데이터·API·기술 의존성을 직접 확인했다.
- 주요 외부 주장에 원출처 또는 복수의 독립 근거가 있다.
- 새로운 검색에서 종합 판정을 바꿀 만한 정보가 더 이상 나오지 않는다.
- 남은 불확실성이 리포트에 기록되고 이를 해소할 방법이 정의되었다.

시간 또는 접근 권한 때문에 조사를 완료하지 못하면 조사 완료로 표현하지 않는다. 미검증 범위와 판정에 미치는 영향을 공개한다.

## 11. 검증 체계

| 검증 영역 | 검증 내용 |
|---|---|
| 목적 타당성 | 문제, 목적, 해결책과 기대 결과의 연결 |
| 문제 실재성 | 대상 환경에서 문제의 존재와 중요도 |
| 도메인 적합성 | 해당 산업의 구조, 관행과 제약 반영 여부 |
| 지역 적합성 | 국가별 시장, 문화, 법률과 데이터 환경 |
| 근거 타당성 | 출처의 신뢰성, 최신성, 적용 가능성과 논리 연결 |
| 데이터 현실성 | 존재, 확보 권한, 품질, 범위, 비용과 지속성 |
| API 현실성 | 기능, 접근 가능성, 제한, 비용과 서비스 지속성 |
| 기술 현실성 | 구현 가능성, 성능, 복잡도와 운영 난이도 |
| 자원 현실성 | 일정, 예산, 인력, 권한과 외부 협력 가능성 |
| 내부 일관성 | 문서 안의 주장, 수치, 정책과 요구사항 충돌 |
| 요구사항 완전성 | 흐름, 상태, 권한, 예외와 경계 조건 |
| 검증 가능성 | 인수 조건과 성과 측정 방법 |
| 운영 지속성 | 보안, 개인정보, 장애, 유지보수와 변경 대응 |

검증 기준은 고정된 문서 양식을 요구하지 않는다. 기획의 단계, 규모, 도메인과 위험에 맞춰 필요한 검증 깊이를 결정한다.

## 12. 판정 체계

### 12.1 문제 심각도

| 심각도 | 기준 |
|---|---|
| 차단 | 핵심 전제가 성립하지 않거나 구현 시작이 불가능함 |
| 높음 | 실패, 법적 문제 또는 대규모 재작업 가능성이 높음 |
| 보통 | 품질, 일정 또는 운영 문제를 발생시킬 가능성이 있음 |
| 낮음 | 실행을 막지는 않지만 명확성이나 완성도를 낮춤 |

### 12.2 종합 판정

| 판정 | 기준 |
|---|---|
| 실행 가능 | 핵심 전제와 실행 조건이 검증됨 |
| 조건부 실행 가능 | 명시된 선행 조건을 충족하면 실행 가능함 |
| 재작성 필요 | 핵심 조사, 결정 또는 명세가 부족함 |
| 실행 불가 | 핵심 전제가 거짓이거나 필수 자원을 확보할 수 없음 |

점수는 비교와 추적을 위한 보조 정보다. 차단 문제가 있으면 평균 점수가 높아도 실행 가능으로 판정하지 않는다.

## 13. 통합 평가 리포트

작성자와 평가자에게 하나의 동일한 리포트를 제공한다.

### 13.1 리포트 구조

1. 종합 판정과 신뢰도

## 14. 이의 제기와 재평가

객관적인 평가도 새로운 증거에 의해 변경될 수 있어야 한다.

- 사용자는 특정 판정에 이의를 제기할 수 있다.
- 반박에는 문서 수정, 데이터, 공식 자료 또는 실제 제약 정보를 첨부할 수 있다.
- NoPlanner는 새로운 증거가 기존 판정을 변경하는지 다시 검증한다.
- 결론을 변경하거나 유지한 이유를 기록한다.
- 수정본에서는 해결, 미해결, 악화 및 신규 문제를 구분한다.
- 문서, 조사 근거, 평가 기준과 판정의 버전을 보존한다.

## 15. 객관성 및 안전 원칙

- 작성자가 사람인지 AI인지에 따라 기준을 바꾸지 않는다.
- 작성자와 평가자에게 서로 다른 사실과 결론을 제공하지 않는다.
- 관계, 직급, 감정과 조직의 기대에 따라 심각도를 조정하지 않는다.
- 문서에 없는 작성자의 성격, 태도와 의도를 추측하지 않는다.
- 확인되지 않은 외부 사실을 단정하지 않는다.
- 평가와 추론을 원문 및 출처까지 역추적할 수 있게 한다.
- 조사할 수 없었던 내용은 숨기지 않고 평가 한계로 표시한다.
- 개인정보, 회사 기밀과 업로드 문서의 외부 전송 범위를 통제한다.

## 17. 필수 시스템 구성

```text
문서 입력
  ↓
문서 파서 및 구조화
  ↓
주장·전제·요구사항 그래프
  ↓
조사 계획기
  ↓
웹·공공데이터·공식 문서·벤치마킹 조사
  ↓
도메인별 검증기 + 내부 일관성 검증기
  ↓
근거 저장소 및 출처 추적
  ↓
판정 엔진
  ↓
통합 평가 리포트
  ↓
이의 제기·수정·재평가
```

LLM 하나의 프롬프트로 전체 평가를 끝내지 않는다. 문서 해석, 조사, 사실 검증, 모순 탐지, 판정과 최종 검토를 분리하고 각 단계의 결과를 저장해야 한다.

## 19. 품질 평가

NoPlanner 자체의 품질도 검증해야 한다.

- 전문가가 찾은 치명적 문제를 얼마나 발견하는가
- 존재하지 않는 문제를 얼마나 적게 생성하는가
- 제시한 출처가 실제 주장과 연결되는가
- 오래되거나 대상 환경과 무관한 자료를 걸러내는가
- 같은 문서를 반복 평가했을 때 핵심 판정이 일관적인가
- 새로운 근거가 들어왔을 때 판정을 적절히 수정하는가
- 문제와 근거를 사용자가 원문까지 추적할 수 있는가
- 개발자가 평가 결과를 실제 구현 판단에 사용할 수 있는가

초기 검증 데이터는 사용자가 실제로 검토했던 회사 기획서를 익명화하여 구성한다. 사용자가 이미 발견한 문제와 NoPlanner의 결과를 비교하고, 누락과 오탐을 기록해 평가 기준을 개선한다.

## 20. 성공 기준

- 개발 시작 전에 차단 수준의 기획 결함을 발견한다.
- 핵심 판정에 원문 또는 외부 출처가 연결된다.
- 데이터와 API의 존재뿐 아니라 실제 확보 가능성까지 확인한다.
- 대상 도메인과 국가에 맞지 않는 근거를 식별한다.
- 문서 내부에서 상충하는 요구사항과 정책을 찾는다.
- 사용자가 기획서 전체를 다시 검토하는 시간을 줄인다.
- 평가 리포트만으로 승인, 반려 또는 재작성 요청의 근거를 설명할 수 있다.
- 수정본이 기존 문제를 해결했는지 자동으로 확인한다.
- 잘못된 판정은 이의 제기와 새로운 근거를 통해 수정할 수 있다.

## 21. 개발 우선순위

### 1단계: 문서 자체 검증

- 문서 입력과 구조화
- 목적, 주장, 전제와 요구사항 추출
- 내부 모순과 누락 탐지
- 근거 없는 주장 식별
- 기본 통합 리포트

### 2단계: 외부 현실 검증

- 자동 조사 계획
- 웹 및 공식 출처 조사
- 공공데이터 탐색
- 데이터·API·기술 확인
- 출처와 신뢰도 관리

### 3단계: 판정 및 재평가

- 심각도와 종합 판정
- 수정본 비교
- 이의 제기와 근거 추가
- 평가 및 근거 이력

### 4단계: 자율 기획

- 평가 기준을 적용한 기획 생성
- 생성 결과 자체 검증
- 결함 자동 보완
- 제품 및 사용자 경험 설계 확장

## 22. 초기 제품의 완료 조건

실제 회사 서비스 기획서를 입력했을 때 다음 결과를 얻을 수 있으면 첫 제품이 성립한다.

1. 문서의 목적, 주장, 전제와 요구사항을 원문 근거와 함께 추출한다.
2. 문서 내부의 주요 모순과 누락을 찾는다.
3. 핵심 데이터, API와 기술 의존성을 외부 자료로 확인한다.
4. 대상 도메인과 국가 환경에 적용 가능한 근거인지 판단한다.
5. 각 문제에 심각도, 신뢰도, 영향과 보완 조건을 제공한다.
6. 구현 가능 여부에 대한 종합 판정을 제공한다.
7. 판정에 사용한 출처와 조사하지 못한 범위를 공개한다.
8. 수정된 기획서를 다시 입력하면 기존 문제의 해결 여부를 비교한다.
