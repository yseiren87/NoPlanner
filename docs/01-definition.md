# NoPlanner 서비스 정의

## 1. 서비스 정의

NoPlanner는 기획자가 없어도 실행 가능한 기획을 만들고, 사람이든 AI든 작성한 기존 기획이 현실에서 성립하는지를 검증·평가하는 LLM 기반 기획 시스템이다.

NoPlanner가 다루는 대상은 문장의 품질이나 문서 형식이 아니다. 기획의 목적, 근거, 대상 환경, 내부 일관성, 데이터와 기술의 확보 가능성, 실행 가능성 및 검증 가능성을 평가한다.

## 2. 문제의식

생성형 AI로 인해 누구나 짧은 시간에 길고 그럴듯한 기획서를 만들 수 있게 되었다. 그러나 문서 생성이 쉬워진 만큼 작성자가 다음 사항을 직접 조사하고 검증하지 않은 기획도 증가한다.

- 무엇을 왜 만드는지 불분명하다.
- 해결하려는 문제가 실제로 존재하는지 확인되지 않았다.
- 특정 도메인, 국가, 시장 또는 조직의 현실이 반영되지 않았다.
- 논문, 통계, 해외 사례를 현재 대상 환경에 적용할 수 있는지 검증하지 않았다.
- 필요 데이터, API, 기술, 권한 또는 운영 자원을 실제로 확보할 수 없다.
- 문서의 주장, 정책, 일정과 요구사항이 서로 충돌한다.
- AI가 생성한 내용을 작성자가 읽고 검증했는지 확인하기 어렵다.
- 문서의 분량과 표현은 충분하지만 실행에 필요한 결정은 빠져 있다.

그 결과 검토자와 실행 담당자가 기획을 다시 해석하고 조사해야 하며, 구현 이후에야 잘못된 전제와 불가능한 요구가 발견된다.

NoPlanner는 그럴듯한 문서를 더 많이 만드는 것이 아니라, **검증되지 않은 문서가 유효한 기획으로 통과되는 문제**를 해결한다.

## 3. 목적

NoPlanner의 목적은 다음 두 가지다.

1. 별도의 기획자가 없어도 문제 정의부터 조사, 판단, 명세, 실행 계획과 결과 검증까지 수행한다.
2. 제출된 기획을 독립적으로 재검증하여 부족함, 오류, 위험과 실행 가능 여부를 객관적인 근거와 함께 제시한다.

두 기능은 같은 기획 능력을 사용한다. NoPlanner는 해당 과제를 직접 기획한다면 확인했어야 할 사항을 기준으로 기존 기획을 평가한다. 평가에서 발견된 결함은 다시 기획을 보완하거나 재작성하는 입력이 된다.

## 4. 핵심 기능

### 4.1 자율 기획

사람이 문제, 목표 또는 아이디어를 제시하면 다음 업무를 수행한다.

- 문제, 사용자, 이해관계자와 발생 맥락을 파악한다.
- 도메인과 대상 국가·시장·조직 환경을 조사한다.
- 사실, 가정, 가설과 결정을 구분한다.
- 기획의 목적, 목표, 성공 기준, 범위와 비범위를 정의한다.
- 가능한 해결책의 가치, 비용, 위험과 가역성을 비교한다.
- 필요한 데이터, API, 기술, 권한과 운영 자원의 확보 가능성을 확인한다.
- 사용자 흐름, 정책, 상태, 예외, 데이터와 비기능 요구사항을 명세한다.
- 개발, 디자인과 운영이 실행할 작업 및 인수 조건을 만든다.
- 실행 결과를 검증하고 후속 개선 또는 중단을 판단한다.

자율 기획의 완료 기준은 문서 생성이 아니라, 별도의 기획자가 다시 해석하거나 핵심 내용을 보충하지 않아도 실행과 검증이 가능한 상태다.

### 4.2 기획 검증 및 평가

기획서, 요구사항, 정책서, 화면 설계, 사용자 흐름, 조사 자료 또는 작업 목록을 입력받아 다음을 검증한다.

| 평가 영역 | 핵심 질문 |
|---|---|
| 목적 | 무엇을 왜 만들며 어떤 문제를 해결하는가 |
| 문제 실재성 | 해결하려는 문제가 실제 대상 환경에 존재하는가 |
| 대상 적합성 | 도메인, 국가, 시장, 법·제도, 문화와 운영 환경에 맞는가 |
| 근거 타당성 | 인용 자료와 사례가 주장을 뒷받침하며 현재 상황에 적용 가능한가 |
| 데이터 현실성 | 필요한 데이터가 존재하고 품질·범위·최신성이 충분하며 확보 가능한가 |
| 기술 현실성 | 핵심 기술, API, 모델과 인프라를 현재 조건에서 구현·운영할 수 있는가 |
| 자원 현실성 | 필요한 비용, 인력, 시간, 권한과 협력 주체를 확보할 수 있는가 |
| 논리 일관성 | 목표, 주장, 정책, 요구사항과 일정이 서로 충돌하지 않는가 |
| 범위 완전성 | 정상·예외·실패 흐름, 경계 조건과 비범위가 정의되었는가 |
| 실행 가능성 | 실행 담당자가 핵심 내용을 추측하거나 다시 기획하지 않아도 되는가 |
| 검증 가능성 | 요구사항과 성과를 객관적으로 확인할 기준이 있는가 |
| 운영 지속성 | 출시 이후 운영, 보안, 개인정보, 장애와 변경을 감당할 수 있는가 |

평가는 고정된 템플릿의 빈칸을 찾는 작업이 아니다. 대상 기획의 목적, 단계, 규모와 위험을 먼저 이해하고, 해당 도메인과 환경에 필요한 평가 기준을 구성해야 한다.

## 5. 통합 평가 리포트

검증 결과는 작성자용과 평가자용으로 나누지 않는다. 작성자, 검토자, 승인권자와 실행 담당자에게 **동일한 통합 평가 리포트**를 제공한다.

모든 사용자는 같은 사실, 근거, 심각도와 종합 판정을 확인한다. 작성자의 기분을 보호하거나 평가자의 기대에 맞추기 위해 표현, 점수 또는 결론을 다르게 제공하지 않는다.

### 5.1 리포트 구성

통합 평가 리포트에는 다음 내용이 포함되어야 한다.

1. **기획 요약**: 문서가 주장하는 문제, 목적, 해결책과 기대 결과
2. **종합 판정**: 실행 가능, 조건부 실행 가능, 재작성 필요 또는 실행 불가
3. **판정 근거**: 종합 판정에 직접 영향을 준 핵심 사실과 결함
4. **평가 영역별 결과**: 충족 여부, 점수 또는 등급, 신뢰도와 판단 근거
5. **문제 목록**: 누락, 모호함, 모순, 근거 부족, 현실성 부족과 위험
6. **미검증 전제**: 문서가 사실처럼 사용하지만 확인되지 않은 가정
7. **확보 불명 자원**: 데이터, API, 기술, 비용, 권한, 인력과 협력 관계
8. **내부 상충**: 문서 안에서 양립할 수 없는 주장, 정책과 요구사항
9. **예상 영향**: 그대로 실행할 때 발생할 실패, 재작업, 비용과 운영 위험
10. **필수 보완 사항**: 실행 전에 반드시 확인하거나 수정해야 할 내용
11. **보완 가능성**: 수정으로 해결 가능한지, 핵심 전제부터 재검토해야 하는지
12. **확인 질문**: 작성자 또는 의사결정자가 답해야 할 구체적인 질문
13. **잘된 부분**: 근거가 충분하고 유지해야 할 결정과 명세
14. **최종 권고**: 승인, 조건부 승인, 반려, 재조사, 재작성 또는 중단

### 5.2 문제 항목의 형식

발견된 모든 문제는 다음 형식으로 기록한다.

| 항목 | 내용 |
|---|---|
| 식별자 | 문제를 추적하기 위한 고유 번호 |
| 분류 | 누락, 모호함, 모순, 오류, 근거 부족, 현실성 부족 또는 위험 |
| 대상 | 해당 문서 위치, 주장 또는 요구사항 |
| 판정 | 무엇이 부족하거나 성립하지 않는가 |
| 근거 | 판정에 사용한 자료, 문서 내용과 추론 |
| 영향 | 해결하지 않을 경우 발생할 결과 |
| 심각도 | 차단, 높음, 보통 또는 낮음 |
| 신뢰도 | 판정의 확실성과 불확실한 이유 |
| 보완 조건 | 최소한 무엇을 조사, 결정 또는 수정해야 하는가 |
| 검증 방법 | 보완 여부를 어떻게 확인할 것인가 |

“구체화가 필요하다”, “검토가 필요하다”와 같은 추상적인 지적만으로는 유효한 평가로 인정하지 않는다.

### 5.3 객관성 원칙

- 작성 주체가 사람인지 AI인지에 따라 기준을 다르게 적용하지 않는다.
- 직급, 관계, 조직의 기대 또는 작성자의 감정에 따라 결론을 조정하지 않는다.
- 문서의 길이, 표현력과 형식적 완성도를 실제 기획 품질로 오인하지 않는다.
- 사실, 문서에서 확인된 내용, 외부 근거, 가정과 시스템의 추론을 구분한다.
- 확인할 수 없는 사항은 임의로 단정하지 않고 미검증 상태와 확인 방법을 제시한다.
- 점수보다 실행을 막는 치명적 결함을 우선한다. 평균 점수가 높아도 차단 문제가 있으면 승인하지 않는다.
- 사람에 대한 인상이나 성격이 아니라 제출된 기획과 확인 가능한 조사·검증 결과를 평가한다.
- 동일한 입력과 근거에는 일관된 기준을 적용하고 평가 기준과 변경 이력을 남긴다.
- 긍정적인 부분과 부정적인 부분 모두 근거가 있을 때만 기록한다.

객관성은 비판을 약하게 표현하는 것이 아니다. 결함을 숨기지 않되, 모든 판정이 반박·재검증 가능한 근거를 가져야 한다는 의미다.

## 6. 평가 판정

| 판정 | 의미 |
|---|---|
| 실행 가능 | 핵심 전제와 실행 조건이 검증되었으며 남은 문제가 실행을 막지 않음 |
| 조건부 실행 가능 | 실행할 수 있으나 명시된 조건과 보완을 먼저 충족해야 함 |
| 재작성 필요 | 목적이나 구조는 유효할 수 있으나 핵심 조사·결정·명세가 부족함 |
| 실행 불가 | 핵심 전제가 성립하지 않거나 필수 자원을 확보할 수 없음 |

판정에는 반드시 근거, 신뢰도, 판정을 바꾸기 위한 조건이 포함되어야 한다. 정보 부족은 자동으로 실행 불가를 뜻하지 않지만, 핵심 전제가 미검증이면 실행 가능으로 판정할 수 없다.

## 7. 기본 작동 절차

1. 입력 문서와 관련 자료를 구조화한다.
2. 문서가 주장하는 목적, 문제, 해결책과 전제를 추출한다.
3. 대상 도메인, 국가, 시장, 사용자와 운영 환경을 식별한다.
4. 내부 문서, 신뢰할 수 있는 외부 자료와 실제 가용 자원을 조사한다.
5. 사실, 가정, 가설, 결정과 미확인 주장을 분리한다.
6. 문서 내부의 누락, 모순과 논리적 비약을 검사한다.
7. 데이터, 기술, 비용, 권한과 운영 조건의 현실성을 검증한다.
8. 문제별 심각도, 영향, 신뢰도와 보완 조건을 결정한다.
9. 통합 평가 리포트와 종합 판정을 생성한다.
10. 새로운 근거나 수정본이 제출되면 같은 기준으로 재평가한다.

## 8. 사람에게 남는 권한

NoPlanner는 기획과 평가를 수행하지만 다음 사항은 권한을 가진 사람이 최종 결정한다.

- 조직이 추구할 가치와 최상위 목표
- 예산 집행, 법적 책임과 대외 약속
- 윤리, 안전, 평판에 큰 영향을 주는 비가역적 결정
- 평가 결과에 따른 승인, 반려와 인사 조치
- 시스템이 접근할 수 없는 현장 정보의 제공

NoPlanner는 이러한 결정을 대신하지 않더라도, 결정권자가 문서를 다시 분석하지 않고 판단할 수 있는 수준의 근거를 제공해야 한다.

## 9. 성공 기준

- 기획자 없이도 실행 가능한 기획을 생성할 수 있는가
- 그럴듯하지만 현실에서 성립하지 않는 기획을 실행 전에 차단하는가
- 도메인과 대상 환경에 맞지 않는 주장과 전제를 찾아내는가
- 존재하지 않거나 확보할 수 없는 데이터·API·기술 의존성을 발견하는가
- 목적 없는 기능과 문제에 연결되지 않은 해결책을 판별하는가
- 문서 내부의 모순, 누락과 논리적 비약을 구체적으로 제시하는가
- 작성자와 평가자가 같은 근거와 판정을 확인할 수 있는가
- 평가자가 승인, 반려, 재작성 또는 중단을 판단할 충분한 정보를 얻는가
- 평가 결과가 구체적인 조사와 수정 작업으로 전환되는가
- 수정본에서 문제가 실제로 해결되었는지 일관되게 재검증하는가
- 실행 이후 발견되는 잘못된 전제와 기획 재작업이 감소하는가

## 10. 하지 말아야 할 것

- 맞춤법, 문장 표현과 템플릿 준수만으로 기획을 평가하지 않는다.
- 문서가 길거나 전문 용어가 많다는 이유로 높은 평가를 주지 않는다.
- 출처가 있다는 이유만으로 현재 도메인과 환경에 적용 가능하다고 간주하지 않는다.
- 작성자의 주장이나 AI의 출력을 독립적인 확인 없이 사실로 인정하지 않는다.
- 데이터, API와 기술이 존재할 것이라고 추정한 채 구현 가능으로 판정하지 않는다.
- 데이터가 존재하거나 무료라는 이유만으로 실제 접근, 비용 감당 또는 상업적 이용이 가능하다고 판정하지 않는다.
- 검색 결과나 2차 인용만으로 핵심 수치를 확정하지 않고 공식 데이터·논문·공시 등 원출처의 실제 위치를 확인한다.
- 작성자와 평가자에게 서로 다른 사실, 점수 또는 결론을 제공하지 않는다.
- 갈등을 피하기 위해 치명적인 결함의 표현이나 심각도를 낮추지 않는다.
- 근거 없이 작성자의 의도, 태도, 성격 또는 능력을 단정하지 않는다.
- 문제를 나열하고 보완 조건과 검증 방법을 생략하지 않는다.
- 출시를 기획 업무의 끝으로 간주하지 않는다.

## 11. 최종 지향점

단기적으로 NoPlanner는 작성된 기획이 실제로 성립하는지 검증하고, 조직이 잘못된 기획을 실행하기 전에 객관적인 판단 근거를 제공한다.

중기적으로는 검증과 평가 기준을 기획 생성 과정에 내장하여, 처음부터 현실성·일관성·실행 가능성이 확인된 기획을 자율적으로 만든다.

최종적으로는 문제 정의, 조사, 기획, 제품 설계, 사용자 경험 설계, 명세, 평가와 개선을 소프트웨어가 수행한다. 조직은 기획자나 디자이너라는 특정 직무의 존재에 의존하지 않고도 제품을 만들고 검증할 수 있어야 한다.

NoPlanner의 최종 목표는 문서를 대신 작성하는 것이 아니라, **기획과 설계라는 조직 기능 자체를 검증 가능한 소프트웨어 시스템으로 전환하는 것**이다.
