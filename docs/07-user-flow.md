# 사용자 흐름

## 1. 기본 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 결과 |
|---|---|---|---|
| 1 | 프로젝트 생성 | 평가 컨텍스트 초기화 | 프로젝트 |
| 2 | 기획서 업로드 | 파일 파싱 및 원문 보존 | 문서 버전 |
| 3 | 국가·도메인·제약 확인 | 문서 추출값과 입력값 병합 | 평가 컨텍스트 |
| 4 | 평가 시작 | 분석 및 조사 계획 생성 | 진행 현황 |
| 5 | 진행 확인 | 검증 작업을 비동기로 실행 | 부분 결과 |
| 6 | 리포트 열기 | 문제와 종합 판정 집계 | 통합 리포트 |
| 7 | 근거 확인 | 원문·외부 출처 표시 | 판정 추적 |
| 8 | 수정본 업로드 | 변경점 분석 및 재검증 | 비교 리포트 |

## 2. 로그인 및 인증 흐름

```text
로그인 페이지
→ Google OAuth 로그인
→ OAuth callback 검증
→ 서비스 JWT 발급
→ JWT를 localStorage에 저장
→ 보호 페이지 진입
→ API 요청마다 Authorization 헤더 전송
```

- 보호 라우트 진입 전 navigation guard가 프론트엔드 인증 상태를 확인한다.
- navigation guard는 JWT 존재 여부와 필수 `exp` 클레임의 만료 여부를 확인한다.
- API는 모든 보호 요청의 JWT를 별도로 검증한다.
- 프론트엔드 인증 상태가 없거나 API가 401을 반환하면 세션 만료 다이얼로그를 표시한다.
- 여러 API가 동시에 실패해도 다이얼로그는 하나만 표시한다.
- 사용자가 `확인`을 누르면 `localStorage`의 JWT와 로컬 인증 상태를 제거하고 로그인 페이지로 이동한다.
- 인증 실패를 감지한 순간부터 새 보호 API 요청과 보호 화면 렌더링을 중단한다.

## 3. 프로젝트 생성

최소 입력은 프로젝트명과 기획 문서다. 국가, 도메인과 대상 사용자를 문서에서 확실히 추출하지 못하면 평가 시작 전에 사용자에게 확인한다. 나머지 정보는 미확인 상태로 평가할 수 있다.

## 4. 평가 실행 상태

```text
대기 → 문서 분석 → 조사 계획 → 외부 조사 → 검증 → 판정 검토 → 완료
                         ↘ 자료 접근 제한 / 사용자 확인 필요
```

장시간 조사는 완료된 결과를 순차적으로 보여준다. 사용자는 평가를 닫아도 이후 다시 진행 상태를 확인할 수 있다.

## 5. 리포트 탐색

기본 화면은 다음 영역으로 구성한다.

- 상단: 종합 판정, 신뢰도, 문제 수, 구현 시작 가능 여부
- 좌측: 원본 문서 및 문서 목록
- 중앙: 문제 목록과 평가 영역
- 우측: 선택한 문제의 근거, 영향과 보완 조건
- 하단 또는 별도 탭: 조사 출처, 평가 한계와 변경 이력

문제 선택 시 원문 위치와 외부 출처를 바로 확인할 수 있어야 한다.

## 6. 이의 제기

1. 사용자가 문제 항목을 선택한다.
2. 반박 설명과 추가 근거를 입력한다.
3. 시스템이 근거의 출처와 적용 범위를 확인한다.
4. 해당 문제와 종합 판정을 재평가한다.
5. 결론을 유지하거나 변경한 이유를 기록한다.

단순히 사용자가 동의하지 않는다는 이유로 문제를 삭제하지 않는다.

## 7. 수정본 재평가

1. 기존 프로젝트에 새 문서 버전을 추가한다.
2. 시스템이 변경된 주장, 전제와 요구사항을 찾는다.
3. 변경 영향을 받는 조사와 평가만 우선 재실행한다.
4. 기존 문제를 해결·부분 해결·미해결·악화·철회로 분류한다.
5. 신규 문제와 종합 판정 변경을 표시한다.

## 8. 예외 흐름

| 상황 | 처리 |
|---|---|
| 문서 파싱 실패 | 실패 위치와 지원 방법을 표시하고 원문 재입력 요청 |
| 국가·도메인 불명 | 핵심 맥락만 사용자에게 확인 |
| 유료·비공개 자료 | 접근 제한과 판정 영향을 기록 |
| 출처 간 충돌 | 양쪽 근거와 차이를 제시하고 신뢰도를 조정 |
| 조사 서비스 장애 | 완료 작업을 보존하고 재시도 |
| LLM 구조화 실패 | 스키마 검증 후 제한 횟수 재시도, 실패 상태 기록 |
| 핵심 전제 확인 불가 | 실행 가능 판정을 보류하고 필요한 확인 방법 제시 |
| 프론트엔드 인증 없음 | 세션 만료 다이얼로그 표시 후 로그인 이동 |
| API JWT 거부 | 진행 중 요청을 중단하고 동일한 세션 만료 흐름 실행 |
| JWT에 `exp` 없음 | 유효하지 않은 토큰으로 처리하고 세션 만료 흐름 실행 |
| JWT 만료 | API 호출 전에 감지하거나 401 응답 시 세션 만료 흐름 실행 |
| Google 검색 설정 없음 | 내부 평가를 계속하고 외부 검증을 건너뜀으로 표시 |
| 선택된 LLM 키 없음 | 평가를 시작하지 않고 필요한 환경변수 이름 표시 |
| 선택 커넥터 키 없음 | 해당 가져오기·내보내기 기능만 비활성화 |

## 9. 동적 검증 흐름

```text
문서 구조화
→ 목적·주장·전제·의존성·위험 추출
→ 적용 가능한 검증기 선택
→ 검증 우선순위와 깊이 결정
→ 선택된 검증 실행
→ 미적용·미검증·건너뜀 사유 기록
→ 종합 판정
```

사용자는 모든 평가 영역이 항상 실행될 것이라고 기대하지 않는다. 진행 화면과 리포트에서 어떤 검증이 왜 선택되었고, 왜 적용되지 않았는지 확인할 수 있어야 한다.

## 10. 후속 자율 기획 흐름

```text
문제·목표 입력
→ 맥락 조사
→ 전제 검증
→ 해결 대안 비교
→ 기획 생성
→ 동일 평가 엔진으로 자체 평가
→ 차단·높음 문제 보완
→ 검증된 기획과 통합 리포트 제공
```
