# 평가 명세

## 1. 목적

이 문서는 NoPlanner가 서비스 기획서를 어떤 기준과 절차로 평가하는지 정의한다. 평가 결과는 작성자와 평가자에게 동일하게 제공하며, 모든 판정은 원문과 외부 근거로 역추적할 수 있어야 한다.

## 2. 평가 단위

평가는 `문서 → 주장·전제·요구사항 → 개별 문제 → 평가 영역 → 종합 판정` 순서로 집계한다.

각 주장은 다음 중 하나로 분류한다.

| 유형 | 정의 |
|---|---|
| 사실 | 신뢰할 수 있는 자료로 확인된 내용 |
| 가정 | 기획 진행을 위해 임시로 참이라고 둔 내용 |
| 가설 | 조사나 실험으로 검증해야 하는 주장 |
| 결정 | 권한자가 선택한 방향 |
| 요구사항 | 구현 및 검증 가능한 필수 조건 |
| 미확인 주장 | 사실처럼 서술되었으나 근거가 없는 내용 |

## 3. 동적 평가 계획

모든 기획에 같은 검증기를 동일한 깊이로 실행하지 않는다. 먼저 기획의 목적, 대상 환경, 주장, 핵심 전제, 의존성과 실패 영향을 분석한 뒤 평가 계획을 구성한다.

1. 종합 판정을 바꿀 수 있는 핵심 전제를 식별한다.
2. 전제마다 사실 확인, 데이터, API, 기술, 법률, 시장, 사용자 또는 운영 검증 필요성을 결정한다.
3. 발생 가능성, 영향과 가역성을 기준으로 검증 우선순위와 깊이를 결정한다.
4. 해당 기획과 무관한 영역은 실행하지 않는다.
5. 선택된 검증을 수행하지 못하면 원인과 판정 영향을 남긴다.

| 상태 | 의미 |
|---|---|
| 충족 | 필요한 검증을 통과함 |
| 부분 충족 | 일부 조건만 확인됨 |
| 미충족 | 근거를 통해 결함이 확인됨 |
| 미검증 | 검증이 필요하지만 자료·권한·설정 부족으로 확인하지 못함 |
| 해당 없음 | 기획의 목적과 의존성상 평가할 필요가 없음 |
| 건너뜀 | 선택 기능이나 연동이 설정되지 않아 실행하지 않음 |

핵심 전제가 `미검증`이면 종합 판정을 `실행 가능`으로 만들 수 없다. `해당 없음`과 `건너뜀`은 낮은 점수나 결함으로 자동 환산하지 않는다.

## 4. 평가 영역

| 코드 | 영역 | 핵심 기준 |
|---|---|---|
| PUR | 목적 타당성 | 문제·목적·해결책·기대효과가 연결됨 |
| PRB | 문제 실재성 | 대상 환경에서 문제의 존재와 중요도가 확인됨 |
| CTX | 맥락 적합성 | 도메인·국가·시장·조직 환경이 반영됨 |
| EVD | 근거 타당성 | 출처가 신뢰 가능하고 주장에 실제로 적용됨 |
| DAT | 데이터 현실성 | 데이터의 존재·품질·접근·비용·상업적 이용 권리·지속성이 각각 확인됨 |
| API | API 현실성 | 기능·권한·제한·가격·지속성이 요구를 충족함 |
| TEC | 기술 현실성 | 기술적으로 구현·운영 가능하며 제약이 반영됨 |
| RES | 자원 현실성 | 일정·예산·인력·권한·협력 주체가 확보 가능함 |
| CON | 내부 일관성 | 주장·정책·수치·요구사항 사이에 충돌이 없음 |
| CMP | 요구사항 완전성 | 흐름·상태·권한·예외·경계 조건이 충분함 |
| VER | 검증 가능성 | 인수 조건과 성과 측정 방법이 객관적임 |
| OPS | 운영 지속성 | 보안·개인정보·장애·유지보수·변경이 고려됨 |

## 5. 문제 유형

- 누락: 필요한 결정이나 정보가 없음
- 모호함: 복수 해석이 가능하고 판정 기준이 없음
- 모순: 동시에 성립할 수 없는 내용이 존재함
- 사실 오류: 확인 가능한 사실과 문서 내용이 다름
- 근거 부족: 주장을 뒷받침할 자료가 없거나 부적합함
- 현실성 부족: 대상 환경에서 전제가 성립하지 않음
- 실행 불가능: 필수 자원이나 기술을 확보할 수 없음
- 과도한 범위: 목적에 비해 비용과 복잡도가 과도함
- 검증 불가능: 완료 또는 성공 여부를 확인할 수 없음
- 위험 미관리: 실패 가능성과 대응책이 다뤄지지 않음
- 이용 불가: 데이터나 API는 존재하지만 라이선스·약관·계약·비용 조건상 해당 제품에서 사용할 수 없음

## 6. 심각도

| 등급 | 판정 기준 | 처리 |
|---|---|---|
| 차단 | 핵심 전제가 거짓이거나 구현 시작 자체가 불가능함 | 해결 전 실행 금지 |
| 높음 | 실패·법적 문제·대규모 재작업 가능성이 높음 | 실행 전 필수 보완 |
| 보통 | 일정·품질·운영에 유의미한 문제가 예상됨 | 계획에 보완 반영 |
| 낮음 | 실행을 막지 않으나 명확성과 품질을 낮춤 | 권고 사항 |

심각도는 문장 표현이 아니라 발생 가능성, 영향 범위, 복구 비용과 가역성으로 정한다.

## 7. 신뢰도

| 등급 | 기준 |
|---|---|
| 높음 | 원문과 신뢰도 높은 직접 근거가 있으며 반대 근거가 없음 |
| 보통 | 복수 간접 근거가 일치하지만 일부 조건이 미확인임 |
| 낮음 | 제한된 자료 또는 추론에 의존하며 추가 확인이 필요함 |

신뢰도가 낮은 문제도 잠재 영향이 크면 차단 후보로 표시할 수 있으나, 확인된 사실처럼 단정하지 않는다.

## 8. 종합 판정

| 판정 | 조건 |
|---|---|
| 실행 가능 | 차단·높음 문제가 없고 핵심 전제가 검증됨 |
| 조건부 실행 가능 | 선행 조건으로 해결 가능한 높음 문제가 존재함 |
| 재작성 필요 | 목적·전제·구조 또는 핵심 명세가 광범위하게 부족함 |
| 실행 불가 | 핵심 전제가 거짓이거나 필수 자원 확보가 불가능함 |

종합 점수는 보조 지표로만 사용한다. 차단 문제는 평균 점수로 상쇄할 수 없다.

## 9. 판정 절차

1. 문서의 목적, 대상, 주장, 전제, 요구사항과 의존성을 추출한다.
2. 문서 내부에서 누락, 모순과 불명확한 참조를 찾는다.
3. 핵심 전제별 검증 질문과 필요한 근거를 정의한다.
4. 내부 자료와 외부 원출처를 조사한다.
5. 각 문제에 영역, 유형, 근거, 영향, 심각도와 신뢰도를 부여한다.
6. 반대 근거와 대안 설명을 검토한다.
7. 차단 문제를 우선하여 종합 판정을 결정한다.
8. 별도 검토 단계에서 근거와 결론의 연결을 재검증한다.

## 10. 객관성 규칙

- 사람과 AI가 작성한 문서에 동일 기준을 적용한다.
- 직급, 관계와 감정은 평가 입력으로 사용하지 않는다.
- 문서의 길이와 표현력을 품질로 간주하지 않는다.
- 확인하지 못한 내용은 `미확인`으로 남긴다.
- 모든 부정·긍정 판정에 근거를 요구한다.
- 평가 기준 버전과 사용 모델을 기록한다.
- 새로운 증거가 들어오면 기존 판정을 변경할 수 있다.

## 12. 평가 금지 사항

- 출처 없는 외부 사실로 결론 내리기
- 검색 결과 제목만 보고 근거로 사용하기
- 단순히 “검토 필요”라고 작성하기
- 작성자의 의도·태도·성격을 추정하기
- 불확실성을 숨긴 채 단일 점수만 제시하기
- 기술이 이론적으로 가능하다는 이유로 현실적으로 구현 가능하다고 판정하기
