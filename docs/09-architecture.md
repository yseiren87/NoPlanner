# 기술 방향

## 1. 문서 목적

이 문서는 NoPlanner 제품 기획을 구현할 때 필요한 대략적인 기술 방향과 시스템 책임만 정의한다. 서비스 분할, 패키지 구조, API, protobuf, 데이터베이스 스키마, 라이브러리와 배포 구성은 여기서 확정하지 않는다.

구현 구조는 개발 시점의 저장소 상태와 `AGENTS.md`, 설치된 아키텍처 스킬, 규칙 및 플러그인을 기준으로 결정한다. 이 문서보다 해당 구현 규칙을 우선한다.

## 2. 기본 기술 방향

| 영역 | 방향 |
|---|---|
| Backend | Go 기반 MSA |
| Backend communication | gRPC 및 Protocol Buffers |
| Frontend | React + TypeScript |
| UI | Tailwind CSS + shadcn/ui |
| 인증 | Google OAuth + 서비스 JWT |
| 작업 처리 | Redis 기반 비동기 처리 |
| 데이터 저장 | 관계형 데이터베이스와 문서 저장소 |
| 실행 환경 | 로컬 실행 우선 |

표에 명시되지 않은 구체적인 제품, 프레임워크, 라이브러리와 구조는 구현 단계에서 아키텍처 규칙에 따라 결정한다.

## 3. 개념적 시스템 책임

NoPlanner는 구현 방식과 무관하게 다음 책임을 가져야 한다.

| 책임 | 역할 |
|---|---|
| 사용자 및 접근 관리 | 로그인, 프로젝트 접근 권한과 세션 관리 |
| 프로젝트 관리 | 기획 맥락, 입력 자료, 평가와 변경 이력 관리 |
| 문서 처리 | 문서 입력, 원문 보존, 구조 추출과 위치 연결 |
| 기획 분석 | 목적, 주장, 전제, 요구사항과 의존성 추출 |
| 검증 계획 | 기획별로 필요한 검증 항목, 우선순위와 깊이 결정 |
| 조사 및 근거 | 외부 자료 조사, 원출처 확인과 근거 추적 |
| AI 공급자 통신 | LLM 생성과 AI 웹 검색 호출, 공급자 응답 정규화와 비밀값 격리 |
| 평가 | 결함, 영향, 심각도, 신뢰도와 종합 판정 생성 |
| 리포트 | 작성자와 평가자가 함께 보는 통합 결과 제공 |
| 재평가 | 수정본 비교, 이의 제기와 판정 변경 이력 관리 |
| 자율 기획 | 신규 기획 생성과 평가 결과 기반 자동 보완 |
| 제품 설계 | 사용자 흐름, 화면 명세와 실행 가능한 UI 산출물 생성 |
| 구현 검증 | 기획과 실제 코드 또는 실행 결과의 일치 여부 확인 |

이 책임들은 기본적으로 논리적 구분이다. 단, LLM과 AI 검색 공급자 통신은 비밀값·공급자 차이·장애 처리를 격리하기 위해 전용 Intelligence MSA로 분리한다. Intelligence는 기획 판단이나 제품 데이터를 소유하지 않는다.

## 4. 전체 처리 흐름

```text
기획 또는 아이디어 입력
→ 문서와 맥락 구조화
→ 목적·주장·전제·의존성·위험 분석
→ 필요한 검증 계획 구성
→ 내부 일관성 및 외부 현실 조사
→ 근거 기반 평가와 종합 판정
→ 통합 평가 리포트
→ 보완·재작성·자율 기획·제품 설계
→ 수정본 또는 구현 결과 재검증
```

모든 기획에 같은 검증 단계를 강제하지 않는다. 기획의 내용과 위험에 따라 필요한 검증만 선택하고, 선택 이유와 적용하지 않은 이유를 보존한다.

## 5. LLM 공급자

다음 공급자를 환경 설정으로 선택할 수 있어야 한다.

- Claude
- Grok
- OpenAI

기본 공급자와 모델을 Intelligence 서비스에 설정하고, 필요하면 분석·조사·평가 단계별로 다른 공급자와 모델을 사용할 수 있어야 한다. 다른 서비스는 공급자 API나 키를 직접 사용하지 않고 내부 gRPC 계약만 사용하며, 공급자별 API 차이는 제품 기능에 노출하지 않는다.

모든 LLM과 AI 검색 키는 Intelligence 서비스 실행 환경에서 설정하며 화면에서 입력받지 않는다. 선택된 공급자의 키가 없으면 관련 작업을 시작하지 않고 설정 오류를 표시한다. 공급자 장애로 다른 모델을 사용하면 평가 이력에 기록한다.

LLM 한 번의 호출로 최종 판정을 만들지 않는다. 문서 해석, 조사 계획, 근거 비교, 문제 생성과 최종 판정 검토를 구분하고 각 결과를 추적할 수 있어야 한다.

## 6. 검색 및 외부 조사

일반 인터넷 검색은 Intelligence 서비스가 Gemini API의 Google Search Grounding을 사용해 수행한다. 별도의 Programmable Search Engine이나 검색 엔진 ID에 의존하지 않는다. Grounding 결과 자체를 근거로 간주하지 않고 원출처를 찾기 위한 수단으로만 사용한다.

- Gemini API 키와 Grounding 지원 모델이 있으면 외부 조사를 수행한다.
- 검색 응답에서 실제 실행 질의, 출처 URL과 인용 연결을 수집한다.
- 조사 기능은 반환된 출처 URL로 직접 이동해 본문, 최종 URL, 확인 시점과 콘텐츠 해시를 보존한다.
- Gemini가 합성한 문장이나 검색 스니펫만으로 사실·수치·가격·라이선스를 확정하지 않는다.
- 키 또는 Intelligence 연결이 없으면 문서 내부 평가는 계속한다.
- 수행하지 못한 외부 조사는 `건너뜀`, 관련 전제는 `미검증`으로 표시한다.
- 핵심 전제가 미검증이면 `실행 가능`으로 판정하지 않는다.
- 공공데이터나 외부 API 키가 없으면 공개 자료를 우선 조사하고, 불가능하면 미검증으로 남긴다.

## 7. 비동기 작업

문서 분석, 외부 조사, 평가와 자율 기획은 오래 걸릴 수 있으므로 비동기로 처리한다. Redis를 작업 전달에 사용하되 구체적인 라이브러리와 처리 구조는 구현 단계에서 결정한다.

제품은 다음 동작을 보장해야 한다.

- 진행 상태 확인
- 단계별 실패와 원인 표시
- 안전한 재시도
- 중복 실행 방지
- 중단 이후 가능한 지점부터 재개
- 완료된 부분 결과 보존

## 8. 인증

- Google OAuth로 사용자를 인증한다.
- OAuth 클라이언트의 내부·외부 사용자 정책은 운영 설정을 따른다.
- 서비스 API 인증에는 JWT를 사용한다.
- JWT는 브라우저 `localStorage`에 저장한다.
- 모든 JWT에 `exp`를 포함한다.
- 보호 화면은 navigation guard에서 토큰 존재와 만료를 확인한다.
- 보호 API 요청은 `Authorization: Bearer <JWT>` 헤더를 사용한다.
- API도 서명과 필수 클레임 및 만료를 독립적으로 검증한다.
- 화면 또는 API 중 어느 하나라도 인증 실패를 감지하면 세션 만료 다이얼로그를 한 번만 표시한다.
- 사용자가 확인하면 저장된 인증 정보를 제거하고 로그인 화면으로 이동한다.
- 만료된 사용자는 Google OAuth로 다시 로그인한다.

`localStorage` 사용에 따른 XSS 위험을 줄이기 위해 콘텐츠 보안 정책, 출력 이스케이프와 외부 스크립트 제한을 적용한다. 토큰과 비밀값은 URL, 로그, 오류 메시지와 분석 이벤트에 포함하지 않는다.

## 9. 설정 및 폴백

환경 설정 파일의 이름, 위치와 형식은 제품 기획에서 고정하지 않는다. 저장소의 `AGENTS.md`, 아키텍처 스킬과 각 플랫폼 규칙을 따른다.

| 설정 누락 | 제품 동작 |
|---|---|
| 선택된 LLM 키 | 관련 작업 시작 차단 및 설정 오류 표시 |
| Gemini Google Search Grounding 설정 | 내부 평가 진행, 외부 검증은 제한된 조사로 표시 |
| Intelligence 서비스 연결 | LLM·AI 검색 작업 차단, 가능한 내부 규칙 검사는 유지 |
| 선택 커넥터 키 | 해당 연동만 비활성화 |
| 외부 데이터 API 키 | 공개 자료로 대체하거나 미검증 처리 |
| 인증 필수 설정 | 로그인 기능 시작 차단 |
| 필수 저장·작업 인프라 | 해당 기능 시작 차단, 가능한 읽기 기능 유지 |

설정 누락을 검증 성공으로 처리하지 않는다.

## 10. 로컬 실행

전체 제품 흐름은 개발자 한 명의 로컬 환경에서도 실행할 수 있어야 한다.

- 기획서 입력부터 조사, 평가, 리포트와 재평가까지 실행 가능
- 자율 기획과 제품 설계 실행 가능
- 로컬에서 필요한 외부 키와 연결 정보를 설정 가능
- 실제 비밀값은 버전 관리에서 제외
- 중단 후 데이터와 평가 상태 복구 가능

구체적인 실행 명령, 컨테이너, 포트와 환경 파일 구성은 저장소의 플랫폼 규칙에 따라 구현한다.

## 11. 보안 및 추적성

- 업로드 문서와 프로젝트는 권한이 없는 사용자에게 노출하지 않는다.
- Intelligence 서비스를 통해 외부 LLM과 검색 서비스로 전송되는 정보와 범위를 기록한다.
- 민감정보는 정책에 따라 마스킹하거나 외부 전송을 차단한다.
- 모든 판정은 원문, 외부 근거, 평가 기준과 모델 버전으로 역추적할 수 있어야 한다.
- 사용자 이의 제기와 재평가로 판정이 바뀌면 이전 결과와 변경 이유를 보존한다.
- 문서에 포함된 프롬프트 인젝션은 명령이 아니라 분석할 문서 내용으로 취급한다.

## 12. 구현 단계의 책임

다음 사항은 제품 기획의 확정 대상이 아니다.

- 서비스와 패키지의 실제 분할
- API 및 protobuf 메시지 구조
- 데이터베이스 테이블과 인덱스
- Go와 React 라이브러리 선택
- 메시지 큐 라이브러리와 작업자 구조
- 파일 저장소 구현체
- 배포 단위, 포트와 컨테이너 구성
- 코드 디렉터리와 import 구조

이 항목들은 구현 시점에 `AGENTS.md`, 관련 아키텍처 스킬, 규칙과 플러그인을 적용해 결정한다.
