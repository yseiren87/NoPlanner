# 테스트 계획

## 1. 목적

NoPlanner는 일반적인 기능 정확성뿐 아니라 평가 결과의 사실성, 재현성, 추적성과 유용성을 검증해야 한다.

## 2. 테스트 수준

| 수준 | 대상 |
|---|---|
| 단위 테스트 | 판정 규칙, 파서, 상태 전이, 점수 집계 |
| 계약 테스트 | protobuf 호환성, gRPC 요청·응답과 오류 코드 |
| 통합 테스트 | 서비스·DB·객체 저장소·큐·외부 어댑터 연결 |
| E2E 테스트 | 업로드부터 리포트와 재평가까지 사용자 흐름 |
| 평가 품질 테스트 | 결함 탐지, 근거 정확성, 오탐과 판정 일관성 |
| 보안 테스트 | 권한, 기밀 전송, 악성 문서와 URL 처리 |

## 3. 기준 데이터셋

초기에는 사용자가 실제로 검토했던 회사 기획서를 익명화하여 골든 데이터셋을 만든다.

각 사례에는 다음을 기록한다.

- 대상 국가와 도메인
- 확인된 핵심 결함
- 결함의 원문 위치
- 검증에 사용한 근거
- 기대 심각도
- 허용 가능한 종합 판정
- 전문가가 논쟁할 수 있는 항목
- 문서 수정 전후 버전

회사 기밀과 개인정보는 제거하거나 합성 데이터로 대체한다.

## 4. 평가 품질 지표

| 지표 | 의미 |
|---|---|
| 차단 문제 재현율 | 전문가가 지정한 차단 문제 중 탐지 비율 |
| 문제 정밀도 | 생성한 문제 중 실제 유효한 문제 비율 |
| 근거 정확도 | 출처가 판정을 실제로 뒷받침하는 비율 |
| 인용 정확도 | 원문 위치와 외부 인용이 올바른 비율 |
| 판정 일관성 | 반복 실행에서 핵심 판정이 유지되는 비율 |
| 환경 적합성 | 국가·도메인이 다른 근거를 잘못 적용하지 않는 비율 |
| 수정 민감도 | 결함 수정 후 해당 문제를 해결로 판단하는 비율 |
| 변경 국소성 | 무관한 수정으로 기존 판정이 불필요하게 바뀌지 않는 정도 |
| 검증 선택 정확도 | 기획의 전제와 위험에 필요한 검증기를 선택한 비율 |

초기 통과 기준의 구체적인 수치는 골든 데이터셋 규모와 사람 평가자 간 일치도를 측정한 뒤 확정한다.

## 5. 필수 시나리오

### 문서 분석

- 목적이 없는 문서
- 같은 정책이 서로 다르게 정의된 문서
- 표와 본문의 수치가 충돌하는 문서
- 여러 문서 사이 요구사항이 충돌하는 경우
- 스캔 PDF와 일부 파싱 실패 문서

### 외부 검증

- 존재하지 않는 API에 의존한 기획
- API는 존재하지만 필수 필드가 없는 경우
- 데이터는 존재하지만 대상 국가가 다른 경우
- 오래된 통계가 최신 사실처럼 사용된 경우
- 논문 실험 조건을 제품 환경에 적용할 수 없는 경우
- 공식 자료와 2차 자료가 충돌하는 경우
- 유료 또는 비공개 자료에 접근할 수 없는 경우
- 무료 데이터지만 비상업적 이용만 허용되는 경우
- 상업적 이용은 가능하지만 저장·가공·AI 처리 또는 재배포가 제한되는 경우
- 데이터셋은 검색되지만 실제 다운로드·승인·계약 조건을 확인할 수 없는 경우
- 뉴스가 원출처의 수치와 다른 단위·기간·표본으로 재인용한 경우
- 기획서의 수치가 원문에는 없거나 별도 계산을 거쳐야 하는 경우

### 판정

- 차단 문제 하나와 다수의 낮은 문제가 함께 있는 경우
- 정보 부족과 전제 거짓을 구분해야 하는 경우
- 새로운 근거로 기존 문제가 철회되는 경우
- 수정본에서 일부 문제만 해결된 경우

## 6. LLM 평가 테스트

- 구조화 출력 스키마 준수
- 존재하지 않는 출처 생성 여부
- 원문에 없는 주장 추가 여부
- 문서 속 프롬프트 인젝션 무시 여부
- 동일 입력 반복 시 핵심 Finding 안정성
- 모델 변경 전후 회귀
- 반대 근거를 제공했을 때 결론 수정의 적절성

LLM 출력은 문자열 일치가 아니라 필수 사실, 금지 오류와 의미적 판정으로 평가한다.

## 7. Backend 품질 요구

- 핵심 판정 규칙 단위 검증
- 서비스 간 계약 호환성 검증
- 데이터 변경 전후 호환성 검증
- 비동기 작업의 중복 전달과 멱등성 검증
- 작업 중단 후 재개
- 외부 공급자 시간 초과·속도 제한·부분 실패
- 생성 코드 diff의 기준 리비전 일치, `git apply --check`, 경로 범위와 placeholder 테스트 거부
- 저장소 아키텍처 규칙의 책임 경계 준수

## 8. Frontend 테스트

- 핵심 flow 단위 및 통합 테스트
- 문서 업로드와 오류 처리
- 평가 상태 갱신
- 문제 선택 시 원문·근거 연결
- 심각도·신뢰도·판정 표시 일관성
- 수정본 비교
- 키보드 탐색과 주요 접근성 검사
- 주요 화면 E2E 테스트
- 생성된 React·Tailwind CSS·shadcn/ui 변경안의 빌드와 렌더링
- 생성 화면의 접근성·반응형·오류·빈·로딩 상태
- 기존 코드와 기획 요구사항의 추적 연결

## 9. 보안 테스트

- 다른 프로젝트 문서 접근 차단
- Google OAuth callback의 state, redirect URI와 실패 응답 검증
- 만료·위조·잘못된 issuer 또는 audience JWT 거부
- `exp` 클레임이 없는 JWT 거부
- access token 만료 후 refresh 없이 Google OAuth 재로그인 요구
- 로그인 성공 시 JWT의 `localStorage` 저장
- 로그아웃과 인증 실패 시 `localStorage` JWT 제거
- navigation guard의 `exp` 만료 사전 감지
- Authorization 헤더 누락과 변조 처리
- navigation guard 인증 실패 시 보호 화면 차단
- API 401 응답 시 세션 만료 다이얼로그와 로그인 이동
- 동시 401 응답에서 다이얼로그가 중복 표시되지 않음
- 업로드 파일 형식·크기·악성 콘텐츠 처리
- SSRF 및 내부 네트워크 URL 차단
- 문서 기반 프롬프트 인젝션
- 로그와 오류 메시지의 기밀 유출
- URL, 로그와 분석 이벤트에 JWT가 포함되지 않음
- CSP와 XSS 방어 설정 검증
- 외부 모델 전송 정책 준수
- 삭제 및 보존 정책 검증

## 10. 로컬 구성 테스트

- Intelligence 서비스에서 지원하는 각 `LLM_PROVIDER` 값의 설정 검증
- 공급자와 모델 식별자가 맞지 않을 때 시작 실패
- LLM·Gemini Google Search Grounding·OAuth·JWT 비밀값 누락 시 명확한 오류
- Document·Evaluation·Research가 외부 AI 공급자를 직접 호출하지 않고 Intelligence gRPC만 사용하는지 검증
- Intelligence 장애·타임아웃·미설정 오류가 소비 서비스의 제한 상태 또는 설정 오류로 변환되는지 검증
- 로그와 프론트엔드 번들에 비밀값이 포함되지 않음
- PostgreSQL과 Redis 재시작 후 평가 작업 상태 복구
- localhost Google OAuth callback 및 전체 로그인 흐름
- 코드가 참조하는 모든 환경변수가 저장소 아키텍처 규칙에 따른 서비스별 환경 계약에 선언됨
- Gemini API 키 또는 Grounding 모델 누락 시 내부 평가가 계속되고 제한된 조사로 표시됨
- Grounding 출처 URL을 직접 방문하고 최종 URL·본문 위치·확인 시점·콘텐츠 해시를 기록함
- Grounding 합성 답변이나 스니펫만으로 핵심 사실을 확정하지 않음
- 선택 커넥터 키 누락 시 해당 기능만 비활성화됨
- 선택 LLM 키 누락 시 관련 작업만 명확한 설정 오류로 차단됨
- PostgreSQL 또는 Redis 필수 설정 누락 시 소유 서비스가 조기에 실패함
- 환경변수 키를 실행 화면에서 입력받지 않음

### 10.1 동적 검증 테스트

- 데이터 의존성이 없는 기획에서 데이터 검증이 해당 없음으로 처리됨
- API 의존성이 있는 기획에서 API 존재·필드·권한 검증이 선택됨
- 특정 국가 법률에 의존하는 기획에서 지역·법률 검증 깊이가 높아짐
- 핵심 전제가 미검증이면 실행 가능 판정이 금지됨
- 선택하지 않은 검증기와 그 이유가 리포트에 기록됨
- 건너뜀과 해당 없음이 미충족으로 잘못 집계되지 않음

## 11. 출시 게이트

- 차단 문제를 평균 점수로 상쇄하는 결함이 없음
- 모든 외부 사실 판정이 출처 또는 미확인 상태를 가짐
- 원문과 근거 링크의 무결성이 유지됨
- 핵심 골든 사례에서 치명적 회귀가 없음
- 중단된 평가를 재개할 수 있음
- 프로젝트 간 데이터 격리가 검증됨
- 알려진 평가 한계가 사용자에게 표시됨

## 12. 운영 중 품질 개선

- 사용자의 이의 제기와 판정 변경을 익명화해 회귀 사례로 추가한다.
- 오탐, 누락, 잘못된 출처와 적용 범위 오류를 별도로 분류한다.
- 모델·프롬프트·평가 기준 변경 전 골든 데이터셋을 재실행한다.
- 도메인별 사례가 쌓이면 전체 기준과 도메인 전용 기준을 분리한다.
