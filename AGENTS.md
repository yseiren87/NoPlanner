# AGENTS.md

## 1. Project

- Name: NoPlanner
- One-line purpose: an LLM-based planning system. It drafts executable plans without a planner, and checks whether
  existing plans (human- or AI-written) hold up in reality: purpose, evidence, target environment, consistency,
  feasibility.
- Domain / primary users: people who write or review product/service plans (see `docs/01-definition.md`).

## 5. Commands

```bash
# install
(cd frontend/app && npm ci)            # Go modules download on first run

# generate gRPC code (proto/generate.sh; build_one itself is not implemented yet)
make backend-msa-build-development NAME=gateway

# run / dev (env from tools/secrets/<platform>/<service>/.env.local-dev)
make backend-msa [NAME=<service>]
make frontend

# lint / typecheck
(cd backend-msa/<service> && go vet ./...)
(cd frontend/app && npx tsc -b)
```

Windows: `powershell -ExecutionPolicy Bypass -File make.ps1 <target>` (same targets, same behaviour).

Root `make` targets (when installed) are listed in the Repository layout table above.

## 6. Testing

- Framework: Go `testing` (backend), Vitest (frontend)
- Location: `backend-msa/<service>/**/*_test.go`, `frontend/app/src/**/*.test.*`
- Run all: `go test ./...` per service; `(cd frontend/app && npm test)`
- Run one: `go test ./modules/token -run <TestName>` (inside the service); `npx vitest run <file>`
- Known failures: `user/modules/token` (a JWT test uses a fixed 2026-08-13 date) and Vitest on Node 26
  (`localStorage`). Neither is caused by the tooling.

## 7. Architecture boundaries

- Feature ownership: one responsibility per service (see Project-specific paths). `gateway` has no database;
  `intelligence` is the only service that calls the LLM provider.
- Import / layer rules: services talk only through `backend-msa/proto` contracts. Inside a service follow
  `yj-backend-msa` (`apps/` → `services/` → `domains/` / `modules/`). The SPA reaches the backend only through
  `gateway`.
- Generated / vendor code (do not hand-edit): `backend-msa/proto/**/*.pb.go`.

## 8. Coding conventions

- Language / style: Go with `gofmt`; TypeScript strict via `tsc -b`
- Logging: structured `log/slog` JSON with event names (e.g. `grpc_server_started`, `configuration_failed`)

## 9. Do / Don't

### Do

- Keep `.env.examples` in each service in sync when adding env keys.
- When an optional external key is missing, implement the fallback defined in the planning docs and keep going
  (`Progress.md` §1).

### Don't

- Don't mark a `Progress.md` item done while a required user decision or external key is missing. Record the blocker instead.
- Don't give each service the same local `PORT`. Every service runs at once under `make backend-msa`.

---

## 10. Secrets & safety

- Never commit: build output (`dist/`), generated `backend-msa/proto/**/*.pb.go`, `node_modules/`
- Env values: `tools/secrets/<platform>/<service>/.env.*` are committed in plain text (private repo only)
- Destructive commands (require explicit user approval): dropping or resetting databases, any `make *-deploy-*`
